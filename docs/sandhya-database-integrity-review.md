\# AttendAI – Database Integrity and Validation Review



\*\*Contributor:\*\* C Sandhya  

\*\*Contribution Area:\*\* Database Engineering  

\*\*Database:\*\* PostgreSQL 16  

\*\*ORM:\*\* SQLAlchemy 2.0 Async



\## 1. Overview



This document reviews database integrity and validation considerations for the AttendAI workforce attendance management system, based on its existing database schema.



\## 2. Multi-Tenant Data Integrity



AttendAI uses an organization-based multi-tenant architecture.



\- Operational records should remain associated with the correct organization.

\- Queries should enforce organization-level data isolation.

\- Employee and attendance relationships should maintain valid references.

\- Organization-specific identifiers should remain unique where defined by the schema.



\## 3. Attendance Data Validation



The attendance\_records table stores clock-in, clock-out, worked minutes, overtime minutes and attendance status.



Important validation considerations:



\- Clock-out should not be earlier than clock-in for a completed attendance record.

\- Worked minutes and overtime minutes should not be negative.

\- Each employee should have at most one attendance record per date, as defined by the existing unique constraint.

\- Incomplete attendance records should support missing punch information.



\## 4. Break Management



The attendance\_breaks table tracks break start time, end time and duration.



Validation considerations:



\- Break end time should not be earlier than break start time.

\- An active break may have a NULL break\_end value.

\- Break duration should be calculated consistently.

\- Break records should reference valid attendance records.



\## 5. Correction History and Auditability



The attendance\_correction\_history table maintains the history of manual attendance amendments.



\- Previous and updated punch values should be retained.

\- A correction should include a mandatory reason.

\- The correcting user's identity should be traceable.

\- Original attendance information should remain auditable.



\## 6. Anomaly Data Validation



The attendance\_anomalies table stores detected attendance exceptions.



Important considerations:



\- Anomaly severity should use supported values.

\- Detection methods should distinguish rule-based, isolation-forest and hybrid detection.

\- Anomaly records should maintain valid employee references.

\- Resolution notes should support review and investigation.



\## 7. Database Migration Practices



AttendAI uses Alembic for database schema migrations.



Recommended practices:



\- Review autogenerated migrations before applying them.

\- Test migrations against a development database.

\- Keep migration changes small and focused.

\- Verify upgrade and downgrade behavior.

\- Avoid modifying existing production data unintentionally.



\## 8. Conclusion



Database integrity is essential for accurate attendance calculations, reliable timecard exception resolution and transparent correction workflows. Consistent validation, organization-level isolation, referential integrity and audit history help maintain trustworthy AttendAI records.



\*\*Note:\*\* This document provides a review of the existing schema and validation considerations. It does not claim that new database constraints or migrations have been implemented.
